# Flux CD on AKS with Kustomize: Step-by-Step Implementation Plan

This guide shows how to introduce GitOps in this repository using Flux CD on an existing AKS cluster, while keeping the current Kustomize-based structure for `dev` and `prod` overlays.

---

## 1. Goal

Use Flux CD to:

- watch this GitHub repository for declarative changes
- apply Kustomize manifests to AKS automatically
- separate `dev` and `prod` environments via Kustomize overlays
- keep cluster state driven from Git, not manual `kubectl apply` commands

---

## 2. What you already have

Your repo already contains the base Kustomize layout:

```text
kustomize-lab/
├── base/
│   ├── deployment.yaml
│   ├── service.yaml
│   └── kustomization.yaml
└── overlays/
    ├── dev/
    │   └── kustomization.yaml
    └── prod/
        ├── kustomization.yaml
        └── replica-patch.yaml
```

This is a good fit for Flux because Flux can reconcile a Git source and then apply a `Kustomization` that points to either the `dev` or `prod` overlay path.

Before starting, make sure you have:

- an existing AKS cluster
- Azure CLI installed
- kubectl installed
- Flux CLI installed
- a GitHub repository already containing this project
- a GitHub personal access token or a GitHub app installation token

## 4. Prepare Azure and AKS access

1. Sign in to Azure:

```bash
az login
az account set --subscription <subscription-id>
```

2. Get cluster credentials locally:

```bash
az aks get-credentials \
  --resource-group <aks-resource-group> \
  --name <aks-cluster-name> \
  --overwrite-existing
```

3. Confirm cluster access:

```bash
kubectl get nodes
```

If you use an AAD-enabled cluster, install the AKS CLI helper on the machine running the bootstrap:

```bash
az aks install-cli
```

## 6. Bootstrap Flux into AKS

Use GitHub as the Git source of truth.

### Example bootstrap command

```bash
flux bootstrap github \
  --owner=<github-user-or-org> \
  --repository=k8s-demo \
  --branch=main \
  --path=./clusters/aks \
  --personal \
  --token-auth
```

What this does:

- installs Flux components into the AKS cluster
- creates the `flux-system` namespace
- creates a GitRepository and Kustomization for the repo path you specify
- writes the bootstrap manifests and configuration into the GitHub repo

### Important note

For this repo, the `--path` should point to a directory that contains the GitOps base configuration for the cluster. A practical layout is:

```text
clusters/
└── aks/
    ├── flux-system/   # generated by bootstrap
    ├── dev-kustomization.yaml
    └── prod-kustomization.yaml
```

If you want Flux to reconcile the Kustomize overlays directly, you can also point Flux to:

```bash
--path=./kustomize-lab/overlays/dev
```

for dev, and create a separate Flux Kustomization for prod.

## 7. Recommended repo structure for GitOps

A clean structure for this repo could look like this:

```text
clusters/
└── aks/
    ├── flux-system/
    ├── dev-kustomization.yaml
    └── prod-kustomization.yaml
```

The Kustomize content remains in:

```text
kustomize-lab/
├── base/
└── overlays/
    ├── dev/
    └── prod/
```

This keeps the GitOps bootstrap resources separate from the application manifests.

## 8. Sample GitRepository and Kustomization manifests

Below is a sample Flux setup you can add to the repo after bootstrap.

### Sample `GitRepository`

Save this as `clusters/aks/flux-system/gitrepository.yaml`:

```yaml
apiVersion: source.toolkit.fluxcd.io/v1
kind: GitRepository
metadata:
  name: k8s-demo
  namespace: flux-system
spec:
  interval: 1m
  url: https://github.com/TechParadise-Lab/flux-kuz-demo.git
  ref:
    branch: main
```

### Sample `Kustomization` for dev

Save this as `clusters/aks/dev-kustomization.yaml`:

```yaml
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: dev-app
  namespace: flux-system
spec:
  interval: 2m
  path: ./kustomize-lab/overlays/dev
  prune: true
  sourceRef:
    kind: GitRepository
    name: k8s-demo
  targetNamespace: dev
```

### Sample `Kustomization` for prod

Save this as `clusters/aks/prod-kustomization.yaml`:

```yaml
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: prod-app
  namespace: flux-system
spec:
  interval: 2m
  path: ./kustomize-lab/overlays/prod
  prune: true
  sourceRef:
    kind: GitRepository
    name: k8s-demo
  targetNamespace: prod
```

## 9. What Flux will do for this repo

Once the GitRepository and Kustomization are in place, Flux will:

- fetch the repo from GitHub
- build the Kustomize output for the `dev` or `prod` overlay
- apply the resulting YAML to AKS
- continuously reconcile the cluster state with the Git repo

This means that changes to `kustomize-lab/base`, `kustomize-lab/overlays/dev`, or `kustomize-lab/overlays/prod` can be committed and automatically deployed by Flux.

## 11. Recommended deployment workflow

### Make a Git change

For example, update the replica count in `kustomize-lab/overlays/prod/replica-patch.yaml`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 5
```

### Commit and push

```bash
git add .
git commit -m "Update prod replica count"
git push origin main
```

### Observe reconciliation

Flux will automatically detect the change and apply it to AKS.

## 13. Recommended security model

For a production-style setup:

- use a dedicated GitHub repository for cluster configuration
- keep Flux credentials in a Kubernetes secret or GitHub token auth
- use separate `dev` and `prod` Kustomizations
- use least-privilege RBAC for the Flux service account
- keep the `targetNamespace` and environment-specific paths explicit

---

## 14. Suggested implementation sequence

1. Confirm AKS access and kubeconfig.
2. Install Flux CLI locally.
3. Bootstrap Flux into AKS using GitHub as the source of truth.
4. Confirm the `flux-system` namespace and controller pods are healthy.
5. Add `GitRepository` and `Kustomization` manifests for `dev` and `prod`.
6. Commit the repo changes and let Flux reconcile them.
7. Test by changing the replica count or app settings and verifying automatic drift correction.

---

## 15. Final outcome

After completing this plan, your AKS cluster will be running a GitOps workflow with Flux, and the repo will become the source of truth for both `dev` and `prod` deployments.

You will no longer need to run manual `kubectl apply -k` commands for routine updates; Flux will reconcile the cluster from the Git repository.
